### 2.5 What libarchive does **not** do

- Split into volumes: nothing on either side. Writer: "disk 0 of 0" (`zip.c:2221`); readers: ZIP comment "multi-volume Zip files" only in a not-supported note and "CD can't be split" (`la/archive_read_support_format_zip.c:757, 4013`), 7z reader has no volume code (grep 0). Any splitting must happen in the `archive_write_open2` writer callback (raw byte split of the stream; see §6).
- "Relative to selection" paths: the caller sets `archive_entry_set_pathname`; no notion of a source tree.
- ZIP AES (needs a crypto backend), 7z AES (no code at all), 7z non-solid mode, 7z without a temp file.
- Seeking on the output: no writer seek callback exists; ZIP is streaming by design (§2.2), 7z uses its temp file (§2.3).

## 10. Risks (facts + the constraint each imposes)

1. **Process placement.** The plan isolates *parsing untrusted input* (`MASTER_PLAN.md:108, 248-255`); an archive writer consumes trusted local bytes but is the same `.so` and the same libarchive code paths (`archive_entry_*`, compressors) — no document sanctions loading `libfylz_ffi_android.so` (+JNA) into the app process, and REPORT-M2 §4's cold-start argument depends on it never being referenced there (`REPORT-M2.md:85-93`). Writing in `:decoders` needs bytes piped in and out (§3) and, for 7z, a temp directory the isolated process can use (§2.3) — `UNVERIFIED`. Either choice is a recorded architectural decision, not a detail.
2. **Ratchets at the bound.** `FylzV1App.kt` = 2271/2271, `FylzAppShell.kt` = 112/112 (`FylzV1AppSizeTest.kt:20, 23`): every line the Compress sheet adds to `FylzV1App` must be paid for (the two existing create entry points, :699-711 and :1009, and the extract password `AlertDialog` :1580-1607 are candidates to move out).
3. **Two create UIs, two `ArchiveService` instances, two name defaults** (`Fylz-<millis>.zip` vs `Fylz-<yyyyMMdd-HHmmss>.zip`), password only on one (`FylzV1App.kt:699-711, 1009`; `ArchiveToolsOverlay.kt:57, 92, 194-195`).
4. **7z engine choice.** The plan's table names the 7-Zip `.so` (LGPL, separate shared library per §2.2) for 7z write with AES; libarchive's writer exists and is compiled in, writes LZMA1/LZMA2/PPMd/BZip2/Deflate/zstd/copy, is **always solid, has no encryption, and needs a temp file** (§2.3). Its output's compatibility with 7-Zip/p7zip is `UNVERIFIED` here (no cross-tool test harness, §9). Unencrypted 7z via libarchive is technically reachable; encrypted 7z is not.
5. **Sizes up front.** tar (pax) and 7z fix the entry size at header time; a source whose `COLUMN_SIZE` is stale/unknown is truncated or zero-padded silently (`pax.c:1653-1660, 2055-2062`; `7zip.c:749-750, 1662`). Only ZIP streams unknown sizes (`zip.c:1104-1109`). `DocNode.size` is nullable (`DocNode.kt:27`); archive-entry sources report `uncompressed` from the listing (known for ZIP/7z, may be unknown for others).
6. **zip64 default and 4 GiB.** libarchive emits zip64 only when needed (§2.2); FAT32 destinations cap files at 4 GiB − 1 (`PreflightPolicy.VFAT_MAX_FILE_BYTES`) and only vfat is detected; a picker destination has no `filesystemType` and fails with `EFBIG` at write time (SURVEY-M34 §1, §5).
7. **Unicode names.** Bit 11 depends on bionic's `nl_langinfo(CODESET)` (or `hdrcharset=UTF-8`, which only works when the current charset is already UTF-8 because iconv is OFF) — `UNVERIFIED` on device (§2.2). 7z names are UTF-16LE via the same sconv machinery (`7zip.c:564-568`); tar/pax names are raw bytes with `hdrcharset` records.
8. **Timestamps.** SAF gives millis (nullable); ZIP has 2 s DOS time plus the UT extra with 32-bit seconds (`zip.c:1274-1292`) — dates past 2038 overflow the UT field; `TimeT` is 32-bit on armv7 (`lib.rs:69-73`).
9. **Non-seekable destinations.** ZIP and tar.* never seek (data descriptors / sequential); 7z seeks only its own temp file; `archive_write_open2` needs no seek callback (§2.1). So an `openOutputStream` pipe from any provider is a valid sink for every format in the sheet.
10. **Encryption expectations.** The sheet's "password (M5)" cannot be honoured with libarchive AES on this build (stub cryptor, §2.2); ZipCrypto would work but is weak; zip4j stays the only AES-256 writer until a crypto backend lands, which also gates M3.10's zip4j removal ("once the parity tests for create, extract and AES pass", `MASTER_PLAN.md:392`). `build.rs:266-269`'s comment about bundled AES is wrong and should be corrected when touched.
11. **Sources from archive locations.** `fylz.compress` is enabled inside archives; every entry read is a materialisation (`ArchiveEntryCache`, 512 MiB cap, links/encrypted refused, N/2 decompressions on stream formats) and the compress destination cannot be the archive itself (`DestinationChooserSheet.kt:36`); a recursive walk of an archive folder lists through the provider's blocking catalog (§5).
12. **Memory on a phone.** xz level 9 ≈ 674 MiB encoder memory, level 6 ≈ 94 MiB, MT multiplies per thread (`xz.1:779-789, 834`); zstd 22 uses a 128 MiB window (`clevels.h`); `:decoders` has a 256 MB address-space *target* (`MASTER_PLAN.md:252`). Level ceilings per format are a design decision the sheet must encode.
13. **Journal/queue semantics.** ARCHIVE rows today are N items → one Uri with no staging/bytes; `TransferWorker` gates on COPY/MOVE; `recover`/retry ignore ARCHIVE; `cancel` uses `cancelWorkById` (chain poisoning) — the M3.4 plan-in-journal, flag-cancel and `Result.success()` machinery is designed but not landed (§4).
14. **Split volumes** are a raw byte split in the writer callback or nothing; PKWARE-spanned ZIP is not producible; verification of a split set needs app-side concatenation (§6).
15. **Multiple concurrent `ArchiveService`s and the legacy overlay** (`fylz.protect`, `fylz.archive.inspect`) keep zip4j alive; M3.10 removal is gated on AES parity, so the Compress sheet and `createZip` will coexist for a while.
